## 01. 개요

- 5일 동안 개인 또는 팀으로 **서비스 하나**를 만든다. "무엇을 만들든 똑같이 지켜야 하는 것"만 공통, 양은 인원에 맞춤.
- 목표: 화면·기능 나열이 아니라 **문제 정의 → 제작 → 수치로 확인 → 설명**의 이야기.
- 2차에서 추가: ① 1차 이후 배운 것을 실제로 쓰기(메뉴에서 선택) ② "내가 한 것"을 보여주기(포트폴리오·면접에서 설명 가능).

### 쓸 수 있는 도구 (지금까지 배운 것으로 충분)

**1차까지**
- Claude, Claude Code + VS Code, CLAUDE.md · 스킬
- HTML 바이브 코딩, 무료/키 필요한 API(.env)
- 파이썬, pandas, Streamlit, OpenAI API 연동
- Git · GitHub, Streamlit Community Cloud 배포(Secrets)

**1차 이후 새로 배운 것 ✨**
- Claude Code 심화: 서브에이전트 · 훅 · 스킬 · **MCP**(GitHub · Notion · Supabase)
- 데이터: 크롤링 · 데이터 분석 · 차트 · Kaggle 데이터
- 웹 서비스: Flask · SQLite · 폼 검증 · Render 배포 · **Next.js** · **Vercel 배포** · PWA
- DB: **Supabase** (db.md 설계 · RLS · 마이그레이션)
- AI 기능: LangChain · **RAG 챗봇** · OpenAI API
- 자동화: **n8n**(Webhook · 구글 시트 · AI 에이전트) · **Apps Script**
- 디자인·협업: **Claude Design** · GitHub PR · 리뷰 · 노션

### 제작 원칙 (7가지)

1. **실제에 준하는 데이터·상황으로 확인**: 여러 건 + 까다로운 경우. 공개 데이터·크롤링·직접 만든 샘플 사용, 개인정보·회사 내부 자료 금지.
2. **수치 하나 이상으로 개선 확인**: 개선 전후를 지표 1개 이상으로 비교. 소규모(테스트 20~30건, 참가자 3~5명)도 충분.
3. **안정성**: 이상 입력·실패·빈 화면·민감정보를 막고 막는 모습을 보여줌. 키는 `.env`/Secrets에만, DB 사용 시 RLS까지.
4. **재현·공유**: README만 보고 다른 사람이 실행/따라 할 수 있어야 하고 **배포 주소에서 동작**해야 함.
5. **AI 활용 과정 기록**: 프롬프트 변경, CLAUDE.md·스킬·MCP 활용, AI 실수를 잡아 고친 과정.
6. **설계 문서 + 회고**: `PRD.md` · `CLAUDE.md` (DB 사용 시 `db.md`)로 이유를 남기고, 맞바꾼 것과 한계를 회고.
7. **내가 한 것이 보이게** ✨: 내 이름이 붙은 산출물을 남김. 팀은 브랜치 → PR → 리뷰.

> **5일 범위 팁**: 완제품이 아니라 *핵심 흐름 하나를 끝까지 + 실제 데이터로 확인 + 지표 하나 + 문서*. 팀이라도 기능을 늘리기보다 같은 흐름을 더 단단하게.

## 02. 무엇을 만드나?

### 주제 고르기
- 자유 주제. 본인(팀) 직무에서 겪는 업무 문제나 생활 속 불편 중 선택.
- 조건: ① 쓸 사람이 분명 ② 데이터·상황 여러 건으로 시험 가능 ③ 5일 안에 핵심 흐름 하나 완성 가능.
- 팀이면 추가 조건: **팀원 모두 맡을 일이 있다.**
- 주제가 크면 1일차에 줄이기. 예: "여행 플랫폼" → "2박 3일 짐 체크리스트 생성기".

### 서비스 형태
- 웹(HTML · Next.js · Flask) 또는 Streamlit 등 **배포 가능한 것** 하나.
- 1차 프로젝트를 이어서 키워도 됨 → 발표에서 **1차 대비 무엇이 나아졌는지** 보여줄 것.

| --- | --- | --- | --- |
| 개발 | 어떻게 동작하는가 | 구조, 오류 처리, 프롬프트 버전 비교 | 정확도, 응답 시간, 오류율 |
| PO | 왜 이 문제이고, 무엇을 먼저 하는가 | 문제 정의, 우선순위, 성공 지표, 뺀 기능과 이유 | 사전에 정한 성공 지표, 사용자 테스트 결과 |
| 디자인 | 왜 이렇게 생겼는가 | 대안 비교, 화면 결정의 근거, 개선 전후 화면 | 과업 성공률, 소요 시간 |
| 마케팅 | 누구에게 어떻게 알릴 것인가 | 타깃, 핵심 메시지, 채널, 콘텐츠 | 문구 A/B 선호도, 콘텐츠 제작 시간 |

## 04. 평가 기준

### 프로젝트 점수 (100점)
프로젝트 하나에 점수 하나(팀원 동일). 범위는 인원별 범위 기준, "수치로 확인"·"문서·발표"는 직군별 강조점 기준. **코드 품질은 평가하지 않음.**

| 항목 | 배점 | 상 (만점 근처) | 중 | 하 |
| --- | --- | --- | --- | --- |
| 문제 정의 | 15 | 누가, 어떤 상황에서, 왜 불편한지 구체적이고 근거 있음 | 문제는 있으나 사용자·근거가 흐림 | 기능 소개만 있음 |
| 동작·완성도 | 20 | 핵심 흐름이 **배포 주소에서** 실제 데이터 여러 건으로 끝까지 돌아감 (인원별 범위 충족) | 내 PC·예시 데이터에서만 돌아감 | 핵심 흐름이 중간에 멈춤 |
| 수치로 확인 | 15 | 지표로 개선 전후를 비교하고 이유를 설명 | 수치는 있으나 비교·해석 없음 | 수치 없음 |
| 안정성 | 10 | 이상 입력·실패·빈 화면·민감정보 중 2가지 이상 막고 시연 | 1가지만 막음 | 방어 없음 |
| 재현·공유 | 10 | README만 보고 다른 사람이 실행/따라 할 수 있음 | README는 있으나 빠진 단계 있음 | 본인만 실행 가능 |
| AI 활용 과정 | 15 | 프롬프트 변경 기록 · CLAUDE.md · 스킬 활용 · AI 실수 수정 사례 + **고른 메뉴를 실제로 씀** | 일부만 있음 | 기록 없음 |
| 문서·발표 | 15 | 직군의 중심 질문에 답하고 설계 판단·맞바꾼 것·한계를 본인 말로 설명 | 무엇을 했는지만 설명 | 직군 관점이 안 보임 |

### 사람마다 통과 조건 (점수 아님) ✨
한 사람마다 3가지는 필수. 하나라도 빠지면 **보완 제출**.

| # | 통과 조건 | 확인 방법 |
| --- | --- | --- |
| 1 | **내 이름의 산출물 1개 이상** (PR · 문서 · 시안 · 프롬프트 md · 자동화 등) | README 역할 표 · GitHub PR · 파일 기록 |
| 2 | **개인 위임 로그 1개** | `docs/위임로그/이름.md` (6칸 양식) |
| 3 | **발표에서 내가 맡은 부분을 내 말로 1분 이상** | 발표·질의 |

### 직군별 안정성 예시
- **개발**: 빈 입력·잘못된 형식, API 실패·키 누락, 응답이 너무 길거나 이상할 때, (DB) RLS·서버 검사.
- **PO**: 사용자 중간 이탈·데이터 없음 등 예외 상황을 서비스와 기획서에 정의했는지.
- **디자인**: 로딩·에러·빈 화면 상태, 긴 텍스트·작은 화면에서 깨지지 않는지.
- **마케팅**: 생성 콘텐츠·자동 발송 메일에 사실 오류·과장 표현·저작권 문제 확인 단계가 있는지.

## 05. 제출물

모든 제출은 **구글 드라이브**. 제출 폴더 안에 내 폴더(팀은 팀 폴더)를 만들고 아래 제출물과 `제출서.md`를 함께 업로드. **모두 필수.**

- 폴더 이름: `개인_이름` 또는 `팀_팀이름` (예: `개인_김○○`, `팀_예약해조`)
- 링크로 내는 것(GitHub·배포 주소·영상)은 `제출서.md`에 적고, 파일로 내는 것(발표 자료·영상 파일)은 폴더에 바로 업로드.
- 영상·발표 자료 링크는 **링크가 있는 사람 보기 가능**으로 공유 설정 확인.
