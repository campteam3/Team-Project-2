# 2차 프로젝트 팀 구조안 (회의용 초안)

> 작성일: 2026-11-23 · 상태: **초안** (팀 회의에서 주제와 함께 확정)
> 기준 문서: [2차프로젝트_가이드.md](2차프로젝트_가이드.md)
> 이 문서는 **주제와 상관없이 쓸 수 있는 틀**입니다. 주제가 정해지면 빈칸을 채웁니다.

---

## 1. 왜 이 구조인가

- 팀 구성: **개발 1명(팀장) + 디자인 2명**, 세 사람 모두 Claude Code로 직접 구현하고 PR까지 올릴 수 있음.
- 목표
  - 수업에서 배운 것을 실제로 쓴다.
  - 디자인 팀원 두 명이 **각자 자기만의 작업**을 갖는다 (포트폴리오·면접에서 "이 부분은 제가 했습니다").
  - 그러면서도 결과물은 **서비스 하나, 흐름 하나**로 이어진다.
- 피하려는 것
  - 각자 만든 페이지를 모아 놓기만 한 결과물 (가이드는 3인 팀에 "핵심 흐름 1개를 끝까지 + 보조 기능"을 요구).
  - 두 디자이너의 화면이 서로 다른 서비스처럼 보이는 것.
  - 팀장이 팀원 화면을 대신 구현하느라 뼈대와 연결을 못 챙기는 것.

## 2. 핵심 아이디어: 페이지가 아니라 "구간"으로 나눈다

사용자가 서비스에 들어와서 목적을 이루기까지의 흐름 하나를 세 구간으로 나누고, 구간마다 주인을 둡니다.

```
[ 입구 ]  ──────▶  [ 핵심 ]  ──────▶  결과
 랜딩 + 첫 입력      기능 사용 ~ 결과 화면
 (디자인 A)          (디자인 B)

        └──── 뼈대: 데이터 · 기능 로직 · 배포 · 구간 연결 (개발/팀장) ────┘
```

팀원이 "딱히 하고 싶은 페이지"가 없어도 **어느 구간을 맡을지만 고르면** 됩니다.

## 3. 역할

| 사람 | 맡는 구간 | 내 이름의 산출물 | 본인 지표 (예시) | 발표에서 답할 질문 |
| --- | --- | --- | --- | --- |
| 디자인 A | **입구**: 랜딩 + 첫 입력 화면 | 시안, 대안 비교, 본인 PR | 5초 테스트 이해도, 시안 A/B 선호도 | 왜 이렇게 생겼는가 (첫인상·시작) |
| 디자인 B | **핵심**: 기능 사용 화면 ~ 결과 화면 | 시안, 개선 전후 화면, 본인 PR | 과업 성공률, 소요 시간 | 왜 이렇게 생겼는가 (사용 과정) |
| 개발 (팀장) | **뼈대**: DB, 기능 로직, 배포, 구간 연결, 취합 | 구조, 오류 처리, 리뷰·머지 기록 | 응답 시간, 오류율 | 어떻게 동작하는가 |

추가 규칙
- **랜딩이 장식이 되지 않게**: 흐름의 첫 단계(입력 시작)가 랜딩에서 일어나게 하고, 시안 두 개를 비교 테스트해 수치를 남긴다.
- **각자 자기 구간의 로딩·에러·빈 화면 상태**까지 맡는다 (디자인 직군의 안정성 항목).
- **입구 → 핵심으로 넘어가는 지점**은 두 사람 작업이 만나는 곳이므로 팀장이 주인.
- 공통 디자인 규칙(색·글꼴·버튼)은 두 디자이너가 **1일차에 함께** 정한다.

## 4. 기술과 메뉴 (팀장 제안 · 주제에 따라 변경 가능)

3인 팀은 메뉴 **3개 이상** 필요.

| 메뉴 | 어디에 쓰나 | 맡는 사람 |
| --- | --- | --- |
| Next.js (+ Vercel 배포) | 전체 화면과 서버 기능 | 전원 (각자 구간) |
| Supabase DB | 데이터 저장, db.md, RLS | 개발 |
| Claude Design | 공통 디자인 규칙, 시안 | 디자인 A·B |
| (선택) 4번째 | 주제에 맞춰: AI 기능 / n8n 자동화 / Playwright QA / PWA 중 | 회의에서 결정 |

## 5. 저장소 구조

구간별로 폴더를 나눠 서로의 파일을 건드리지 않게 합니다.

```
app/
  page.tsx              ← 랜딩            (디자인 A)
  start/                ← 첫 입력          (디자인 A)
  (core)/               ← 기능 사용·결과    (디자인 B)
  api/ 또는 actions/     ← 서버 기능        (개발)
components/
  ui/                   ← 공용 부품 (버튼·입력 등 / 변경은 PR로 합의)
  entry/                ← 입구 전용         (디자인 A)
  core/                 ← 핵심 전용         (디자인 B)
lib/                    ← DB 연결·기능 로직  (개발)
styles/tokens.css       ← 공통 디자인 규칙   (디자인 A·B 합의)
prompts/                ← 프롬프트 v1 → v2 기록 (각자)
docs/위임로그/           ← 이름.md × 3 + 팀.md
PRD.md · CLAUDE.md · db.md · git.md · README.md
```

## 6. 일하는 방식

- **브랜치 → PR → 다른 팀원 리뷰 → 팀장 머지.** main에 직접 올리지 않는다.
- 브랜치 이름: `이름/작업내용` (예: `a/landing-hero`). 자세한 규칙은 `git.md`에.
- **가짜 데이터로 먼저**: 팀장이 2일차까지 "화면이 주고받는 값"(무엇을 넣고 무엇을 받는지)을 정해 주면, 디자이너는 가짜 데이터로 화면을 만들고 나중에 진짜 데이터로 바꾼다.
- 공용 폴더(`components/ui`, `tokens.css`)를 바꿀 때는 PR에 한 줄로 알린다.
- 매일 아침 스탠드업 10분: 어제 한 것 / 오늘 할 것 / 막힌 것.
- AI에게 맡긴 일은 그때그때 `prompts/`와 위임 로그에 적는다 (5일차에 몰아 쓰지 않기).

## 8. 가이드 요구사항과의 대응

| 가이드 요구 | 이 구조에서 채우는 방법 |
| --- | --- |
| 핵심 흐름 1개 끝까지 + 보조 기능 | 입구 → 핵심 → 결과가 흐름 하나. 보조 기능은 주제에 맞춰 1개 |
| 지표 1개 + 직군별 1개 | 팀 지표 1개 + 디자인 A·B 각자 지표 + 개발 지표 |
| 메뉴 3개 이상 | Next.js · Supabase · Claude Design (+ 선택 1개) |
| 내 이름의 산출물 | 구간별 PR과 시안 |
| 1인당 PR 1개 이상 | 브랜치 → PR 방식으로 자연히 충족 |
| 발표에서 1분 이상 | 각자 자기 구간의 설계 판단을 직접 발표 |
| 위임 로그 | `docs/위임로그/이름.md` × 3 + 팀 1개 |
| 안정성 2가지 이상 | 디자이너: 상태 화면 / 개발: 이상 입력·API 실패·RLS |

## 9. 회의에서 정할 것

1. **주제** — 조건 확인: 쓸 사람이 분명한가 / 여러 건으로 시험할 수 있는가 / 5일 안에 흐름 하나를 끝낼 수 있는가 / 입구와 핵심 양쪽에 디자인할 거리가 충분한가
2. **구간 배정** — 누가 입구, 누가 핵심을 맡을지
3. **팀 지표와 각자 지표**
4. **4번째 메뉴**를 넣을지, 넣는다면 무엇을
5. **공통 디자인 규칙을 정하는 방법** (1일차 몇 시까지, 누가 정리)
6. **리뷰 규칙** — PR을 누가 보고, 얼마나 빨리 봐 줄지

## 10. 대안: 사용자가 두 종류인 주제라면

신청자/운영자처럼 사용자가 둘이면 "사용자 화면 / 관리자 화면"으로 나눌 수도 있습니다. 각 디자이너가 흐름 하나를 통째로 갖는 장점이 있지만, 범위가 커져 5일 안에 끝내기가 더 빠듯합니다. 주제가 정해진 뒤 판단합니다.
