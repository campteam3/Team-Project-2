# 기념 메시지 먼저 보내기 — 설계 (FEEDBACK F1)

> 2026-11-27 · 차명근과 에이전트가 함께 정함 · 담당 차명근
> 작업 마감 **2026-11-29(일) 23:59**. 이 기능도 그 안에 배포까지 끝냅니다.

## 1. 왜 만드나

축하나 기념 메시지는 받는 사람이 "나 축하해 줘", "스노우볼 만들었는데 달아 줘"라고 부탁하기보다, **보내는 사람이 먼저 보내는 경우가 더 많습니다.** 지금 서비스는 부탁하는 흐름(내 스노우볼을 만들어 링크를 보냄)만 있어서, 카카오톡으로 "축하해~"를 보내던 그 순간을 대신할 방법이 없습니다.

설문에서도 15명 중 7명이 "링크를 보내 부탁하기가 민망해서 안 할 것 같다"고 답했고, 2명은 "친구가 대신 만들어 주면 좋겠다"고 했습니다 (`docs/설문결과/요약.md`).

이 기능은 메시지를 **글 한 줄이 아니라 오너먼트 하나로** 먼저 보내서, 받은 사람이 그것을 열어 읽고, 자기 스노우볼에 모아 둘 수 있게 합니다. 메시지가 "모을 수 있는 물건"이 되는 것이 이 서비스의 핵심이고, 이 기능은 그 물건을 보내는 사람 쪽에서 먼저 건넬 수 있게 합니다.

## 2. 목표 · 하지 않을 것 · 실패로 보는 것

**목표**
- 첫 화면에서 "기념 메시지 보내기"로 오너먼트 하나와 메시지를 만들어 링크로 보낼 수 있다.
- 링크를 받은 사람은 가입 없이 그 오너먼트를 열어 메시지를 바로 읽는다.
- 받은 사람은 그 오너먼트를 자기 스노우볼에 달아 보관할 수 있다. 스노우볼이 없으면 만들면서, 있으면 닉네임 + 비밀번호로 들어가서.
- 지금 있는 흐름(내 스노우볼 만들기 → 링크 공유 → 친구가 달기)은 그대로 둔다. 두 방법을 모두 쓴다.

**하지 않을 것 (이번 범위 밖)**
- 오너먼트를 달 **위치를 고르기**. 지금처럼 정면부터 자동으로 달린다.
- **받는 사람 이름** 적기. 비워 둔다. 그래서 단체방에도 그대로 보낼 수 있다.
- 누가 보관할 수 있는지 제한하기. **링크를 연 사람은 누구나** 각자 자기 스노우볼에 달 수 있다. (나중에 팀 회의에서 다시 봄)
- 보낸 메시지를 고치거나 지우기, 만료 기간, 받았다는 알림.
- 생일 같은 다른 기념일 모양 (FEEDBACK F3 · F4).

**실패로 보는 것 (동작은 해도 안 되는 것)**
- 링크가 없는 사람이 남의 기념 메시지를 읽을 수 있음 (링크 번호를 짐작해서 등).
- 지금 있는 흐름(만들기 · 달기 · 읽기 · 지우기)이 깨지거나 느려짐.
- 받은 사람의 첫 화면이 지금 스노우볼 화면보다 눈에 띄게 늦게 뜸.
- 금지어 · 200자 · 39개 같은 지금 규칙을 이 흐름으로 우회할 수 있음.

## 3. 정해진 것

### 3-1. 보내는 사람의 흐름
1. **첫 화면**(`/`, `components/owner/OpeningView.tsx`)에 **[기념 메시지 보내기]** 버튼을 더한다. "내 스노우볼 만들기"가 빨간 주 버튼이므로 같은 도크에 **보조 버튼(유리)** 으로 둔다 (DESIGN.md: 빨간 버튼은 한 화면에 하나).
2. **오너먼트 고르기**: 모양(볼 · 별 · 하트)과 색 6가지. 지금 친구 화면의 고르기(`OrnamentPickDock`)와 같은 선택지. 배경은 3-3 의 "오너먼트 하나만 크게" 장면이고, 고르는 대로 바로 바뀐다.
3. **메시지 쓰기**: 보내는 사람 이름 + 메시지. 지금 친구 화면의 메시지 카드(`MessageCard`)와 같고, 기본 문구(F2)도 그대로 나온다.
4. **보내기**: 저장하고 링크를 보여 준다. [링크 복사]와 [카카오톡으로 보내기]. 지금의 공유 도크(`ShareDock`)를 쓴다. 카카오톡 카드 제목은 **"○○님이 기념 메시지를 보냈어요"** (○○ = 보내는 사람 이름).
5. 받는 사람 이름은 적지 않는다.

### 3-2. 링크
- 주소: `/gift/<기념 메시지 번호>`. 번호는 **짐작할 수 없는 긴 무작위 번호**(UUID)로 한다. 링크를 가진 사람만 읽을 수 있어야 하기 때문이다.
- 링크를 가진 사람은 누구나 메시지를 읽을 수 있다.

### 3-3. 받는 사람이 보는 화면 (A안: 오너먼트 하나만 크게)
- 제목 "○○님이 보낸 오너먼트", 부제 "눌러서 열어 보세요".
- 화면 가운데에 그 오너먼트 **하나만 크게** 떠 있다. 스노우볼은 없다. 배경은 지금 화면들과 같은 겨울 마을 그림.
- 오너먼트를 누르면 **메시지 카드**가 열린다: 보낸 사람 이름, 메시지, 날짜.
- 아래에 **[내 스노우볼에 달기]**(주 버튼)와 **"이미 스노우볼이 있어요"** 링크.
- 오너먼트는 지금 스노우볼에 달리는 것과 **같은 모델 · 같은 질감**을 쓴다 (`public/models/ornaments.glb`). 새로 그리지 않는다.

### 3-4. 보관하기 (내 스노우볼에 달기)
- **스노우볼이 없는 사람**: [내 스노우볼에 달기] → 지금의 만들기 흐름(꾸미기 → 닉네임 · 비밀번호). 다 만들면 그 오너먼트가 **자동으로** 달린 채 완성 화면으로 간다.
- **스노우볼이 있는 사람**: "이미 스노우볼이 있어요" → 닉네임 + 비밀번호 → 맞으면 **바로** 달리고 그 사람의 스노우볼 화면으로 간다.
- 달리는 위치는 지금처럼 **정면부터 자동**.
- 한번 달린 뒤에는 지금 오너먼트와 똑같다: 주인만 읽고, 주인이 지울 수 있다. 보낸 사람 이름과 메시지가 그대로 보인다.
- **같은 스노우볼에 같은 기념 메시지를 두 번 달 수는 없다.** 이미 달려 있으면 그렇다고 알려 주고 그 스노우볼로 보낸다.
- 지금 규칙을 그대로 적용한다: 금지어, 이름 20자 · 메시지 200자, 스노우볼당 39개. 가득 찬 스노우볼에는 달 수 없다고 알려 준다.

### 3-5. 데이터 (DB)
- 기념 메시지는 **새 표**(`snowglobe.gifts`)에 저장한다: 번호(UUID), 보내는 사람 이름, 메시지, 모양, 색, 만든 시각.
- 지금처럼 표는 직접 읽지 못하게 막고(RLS), **DB 함수로만** 쓰고 읽는다 (`lib/api.ts` 에 함수 추가).
- 보관하면 그 내용을 **복사해** 받은 사람의 스노우볼에 오너먼트로 단다. 이후 그 오너먼트는 지금의 `ornaments` 표에 있는 다른 오너먼트와 같다. 어느 기념 메시지에서 왔는지는 기록해 두어 3-4 의 "두 번 달기 막기"에 쓴다.
- 보관한 오너먼트의 **날짜(`created_at`)는 보관한 시각**으로 한다. 기념 메시지를 만든 시각으로 하면, 오너먼트를 `created_at` 순서로 읽어 정면부터 자리를 정하는 지금 방식 때문에 이미 달린 오너먼트들의 자리가 밀려 바뀔 수 있다. 보관한 시각으로 하면 "1분에 10개" 제한도 지금처럼 그대로 적용된다. 메시지 카드에 보이는 날짜도 보관한 날이 된다. *(에이전트의 판단)*
- 보관할 때는 지금의 주인 확인 방식(주인 토큰)을 쓴다. 만들기나 로그인이 끝나면 브라우저에 주인 토큰이 생기므로, 그 토큰으로 "이 스노우볼의 주인이 이 기념 메시지를 단다"를 확인한다.
- 마이그레이션은 `supabase/migrations/` 에 새 파일로, 기존 파일은 고치지 않는다. `db.md` 에 표 · 함수 · 오류 이름을 더한다.

## 4. 제약

- **마감**: 2026-11-29 23:59. 빠듯하면 3-3 의 연출(오너먼트가 떠서 도는 움직임 등)을 줄이고, 흐름(보내기 → 읽기 → 보관)을 먼저 끝까지 동작시킨다.
- **Next.js 16** (App Router, `cacheComponents`). 코드를 쓰기 전에 `node_modules/next/dist/docs/` 의 해당 문서를 확인한다 (`AGENTS.md`). 주소에 따라 미리보기 정보가 바뀌는 화면은 `app/globe/[id]/page.tsx` 와 같은 방식(DynamicMarker)을 따른다.
- **공개 저장소**: 키 · 토큰 · 실제 사람의 메시지를 커밋하지 않는다. 확인용 데이터는 지어낸 것으로, 끝나면 지운다.
- **다른 사람의 파일**: `OpeningView.tsx`, `OwnerFlow.tsx`, `LoginView.tsx`, `Stage.tsx`(김미영), `SnowGlobeGlb.tsx`(이민정)를 고쳐야 할 수 있다. **필요한 만큼 직접 고치고, 머지한 뒤 고친 곳을 이슈(`[To 이름]`)로 알린다.** CLAUDE.md 고정 규율 5 는 "직접 고치지 말고 이슈로"이지만, 이 프로젝트에서는 차명근이 지금까지 같은 방식(소리 버튼 · 이미지 저장 · 기본 문구)으로 진행했고 팀도 이렇게 해 왔다. 고치는 양은 연결에 필요한 만큼으로 줄이고, 모양 · 배치는 두 사람이 나중에 바꿀 수 있게 둔다.
- **휴대폰**: 키보드가 올라올 때의 처리(`Stage` 의 `kb:`)와 아이폰 흔들기 권한 등 지금 동작을 깨지 않는다. 메시지 쓰기는 지금 `Stage` + `MessageCard` 를 쓰면 키보드 처리를 그대로 받는다.
- **로딩**: 받은 사람의 화면은 오너먼트 모델(약 40KB)만 있으면 되므로, 스노우볼 모델(약 900KB)을 받지 않게 한다.

## 5. 만드는 사람에게 맡기는 것

- 파일 · 컴포넌트 이름, 화면 주소의 세부(`/gift/new` 등).
- "오너먼트 하나만 크게" 장면을 어떻게 만들지. 이민정 님 파일의 오너먼트 그리기 코드를 꺼내 쓸 수 있게 고칠지, 같은 모델로 새로 그릴지. 모습이 스노우볼에 달린 오너먼트와 같아 보이면 된다.
- 메시지 카드의 모양 (지금의 메시지 보기 카드 `MessageViewer` 를 쓸지 등).
- 보관 과정에서 기념 메시지 번호를 만들기 · 로그인 화면에 넘기는 방법(주소 뒤에 붙이기 등).
- 이 브라우저에 이미 주인 토큰이 있는 스노우볼이 있으면 "○○의 스노우볼에 달기"를 바로 보여 줄지 (있으면 편하지만 필수는 아님).
- 링크를 붙여 넣었을 때의 미리보기 제목. 서버에서 DB 를 읽지 않으려면 "기념 메시지가 도착했어요" 같은 공통 제목도 괜찮다. 카카오톡 공유 카드는 화면에서 보내는 사람 이름을 알므로 3-1 의 제목을 쓴다.
- 기념 메시지를 몰아서 만드는 것을 막을지, 막는다면 어떻게.

## 6. 확인

- 실제 DB 로: 보내기 → 다른 브라우저에서 열기 → 읽기 → (없는 사람) 만들고 보관 / (있는 사람) 로그인해 보관 → 주인 화면에서 그 메시지가 보이는 것. 같은 스노우볼에 두 번 달기, 가득 찬 스노우볼, 금지어, 없는 번호.
- 링크 없이 읽을 방법이 없는 것: 표 직접 읽기 차단, 없는 번호 · 짐작한 번호.
- 지금 흐름이 그대로인 것: 만들기 · 친구 달기 · 로그인 · 읽기 · 이미지 저장 · 음악.
- PC 와 휴대폰 크기(390 · 320), 배포 주소에서 받은 사람 화면의 첫 로딩 시간.
- `npm run lint`, `npm run build`.
